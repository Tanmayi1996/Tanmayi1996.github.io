# Editorial notes

This portfolio uses a consistent writing approach across user guides, API examples, and tool references.

## Audience and task

Each page is written for a defined reader and a specific task. A writer using the release note composer needs to know which fields to enter and how to review the result. A developer using the API response explorer needs to understand that the displayed request and response are examples, not live service output.

## Voice and point of view

Address the reader directly. Prefer active voice and present tense. Use imperative verbs in procedures.

| Prefer | Avoid |
|---|---|
| Enter a product name. | A product name should be entered. |
| Select **Generate draft**. | The Generate draft button should be clicked by the user. |
| Review the output before you publish it. | It is recommended that the output undergo review prior to publication. |

## Headings and procedures

Use sentence-style capitalization. Headings describe the task or subject. Use numbered steps when order matters, and keep each step focused on one action.

## UI and code formatting

Use bold for visible UI labels, such as **Generate draft**. Use code formatting for identifiers, literal values, paths, commands, and code, such as <code>status</code>, <code>GET /v1/projects</code>, and <code>index.html</code>.

## Accuracy and limitations

Document what the implementation does today. Do not imply that an interactive example performs a network request, persists data, or validates a production system when it does not. State limitations near the relevant procedure.

## Accessibility

Use meaningful link text, descriptive image alternatives, headings in logical order, and controls with accessible names. Procedures should not depend only on color or spatial direction.

## Public references
